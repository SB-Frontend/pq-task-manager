# Personal Project Task Manager

## 1. Project Goal

Build a small, clean, fast personal project/task management application for a frontend developer.

The application is primarily for tracking work across multiple projects.

I receive development tasks, work on them over a period of time, complete them, and need to maintain a clear record of:

* What project the task belongs to
* What I need to do
* What I am currently working on
* What is pending
* What has been completed
* What changes/work were performed
* How much time was estimated
* How much time was actually spent
* When the task was started and completed

The application should remain intentionally small and simple.

Do NOT turn this into Jira, Linear, Trello, or a complex enterprise project-management application.

The primary goal is personal work tracking.

---

# 2. Core Concept

The application hierarchy should be:

Project
└── Tasks
└── Work Logs

A project contains multiple tasks.

Each task belongs to exactly one project.

A task can have multiple work-log entries describing what was done during different work sessions.

Example:

Project:
"Company Website"

Task:
"Implement responsive navigation"

Status:
"In Progress"

Work logs:

* 24 Aug — Created navigation component
* 25 Aug — Added mobile menu
* 26 Aug — Fixed tablet responsive issues

---

# 3. Recommended Technology

Use a modern, simple, production-ready frontend stack.

Preferred:

* Next.js
* TypeScript
* Tailwind CSS
* React
* Reusable component architecture

Before implementing anything:

1. Inspect the existing repository.
2. Check whether a project already exists.
3. Check package.json and existing dependencies.
4. Do not unnecessarily replace the existing setup.
5. Reuse existing conventions where reasonable.
6. If the repository is empty, create the appropriate Next.js application structure.

The application should be deployable to Vercel.

Use the simplest architecture that satisfies the requirements.

Do not introduce unnecessary abstractions.

---

# 4. Data Persistence

The application should support persistent data.

First inspect the existing project and determine the simplest appropriate solution.

For a single-user application, prefer a simple database/storage solution rather than building unnecessary backend infrastructure.

The architecture should allow the storage layer to be replaced later if required.

Do not hard-code application data into components.

Keep data access separate from UI components.

If a database is required, keep the schema small and clear.

# 17. Task Status Behavior

When a task changes to:

### In Progress

If no start date exists, optionally set the start date.

### Completed

Set completion date automatically if it is empty.

Do not overwrite an existing manually entered date without confirmation.

### Reopened

If a completed task is moved back to In Progress, preserve the previous completion date/history if possible.

Keep this behavior simple.

Do not silently delete projects or tasks.

Show confirmation.

Example:

"Delete this task?"

"This action cannot be undone."

---

# 28. Architecture Requirements

Keep the codebase organized.

Suggested structure:

app/
components/
lib/
types/
hooks/
services/

Exact structure may be adjusted based on the existing repository.

Keep:

* UI components separate from data logic
* Types centralized where appropriate
* Database/storage access separated from UI
* Export functionality isolated
* Reusable forms shared between create/edit flows

Avoid putting all application logic into one large page component.

---

# 29. Important Development Rules

Before writing code:

1. Inspect the repository.
2. Understand the current stack.
3. Identify existing components and conventions.
4. Create a short implementation plan.
5. Identify the smallest set of files that need to change.
6. Then implement.

Do not rewrite unrelated code.

Do not install dependencies unless they are actually required.

Do not create unnecessary files.

Do not introduce unnecessary architecture.

Do not implement features that are not listed here unless they are required for correctness.

If there is a better technical approach than the one specified here, explain it briefly before making a major architectural change.

# 31. Definition of Done

The application is complete when I can:

1. Create a project.
2. Open a project.
3. Create tasks under that project.
4. Set task status.
5. Set task priority.
6. Track estimated and actual time.
7. Add work logs.
8. Record what changes I made.
9. See pending tasks.
10. See tasks currently in progress.
11. See completed tasks.
12. Search tasks.
13. Filter tasks.
14. View project progress.
15. See recent activity.
16. Export tasks to Excel.
17. Export work logs.
18. Use the application on desktop and mobile.
19. Deploy the application to Vercel if the selected architecture supports it.

---

# 32. Important Product Principle

Keep asking:

"Does this feature help a frontend developer understand what they worked on, what is pending, and what they completed?"

If the answer is no, do not add the feature to v1.

The goal is a small personal work tracker, not a complete project-management platform.

Start by inspecting the repository and proposing the implementation plan before making large changes.
